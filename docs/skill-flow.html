How the skill builds a design

Hagen Design System Base · skill 2.13 · updated 24 Nov 2026 · click a step to see how it works under the hood · Terms

Terms

Files

Base (tier 1)
The shared file "Design System Base". Plain parts, tokens and rules every app uses. Its Inter typeface and colors are placeholders.
App file (tier 2)
One Figma file per app, such as the trial app or the first app. It uses the base as a library and holds the app’s own look and rules.
Tier 2 Template
A clean app file you duplicate to start a new app. It already has the agent pages, blocks, text styles and 15 starter wraps.
Agent pages
Pages in a file written for agents to read: AGENT RULES, AGENT PROGRESS, AGENT ROADMAP in the base; AGENT RULES (PROJECT), AGENT BRIEF and AGENT SITEMAP in an app file.
Spec block
A text block on an agent page that an agent can find by name and read in parts. RULES, FLOWS, MAPPING and CHANGELOG are spec blocks.

Blocks the agent reads

RULES
The approved rules of a file. Read in full every session. It also has a "What to read, and when" table that says which other blocks a task needs.
HANDOFF
A short note in the base PROGRESS block: what the last session did and what the next one should do. It lets a new session start without context.
BRIEF and SITEMAP
The app’s goal, audience and features (BRIEF), and the numbered tree of every screen and state (SITEMAP).
MAPPING
The table of an app’s parts: which base part each one uses, and whether it is a wrap, fork or local part.
CHANGELOG
The dated log of changes. Agents read only its top lines and add one line per change.
FINDINGS
Gaps in the base that an app ran into, such as a missing part or a color a wrap can’t change. Each one is a T item.
SKILL FINDINGS
Lessons about how agents work, such as a correction you made or a repeated mistake. Each one is an SF item. Only you approve them.

Working together

Lock
A row in the LOCKS block of the base file saying which session is editing which base part right now. A "do not touch, I’m working here" sign for the base.
Claim
The same sign in an app file: a line in the Claims section of its RULES block. It names the session, what it owns (pages, flow sections, parts) and the date. It is removed when the session ends.
Stamp ("Built on")
A line on an app’s RULES block saying which base rules version and skill version the app was last checked against. Agents compare it at the start of a session.
Your OK
Your explicit approval in chat. "Looks fine" does not count. Needed for every rule, token or component change, and at the end of each new app stage.
Rules maintenance OK
A separate OK to change the rules pages themselves, such as adding a block. An OK to build a screen is not one.

Parts

Token / variable
A named value (color, spacing, radius, size) stored in Figma variables. Screens use tokens, never raw numbers.
Wrap
An app part that holds a base part inside and restyles it with the app’s colors and text styles. Named like the trial app/Button. The default way to make an app part.
Fork
An app copy of a base part with a changed structure. Only when a wrap can’t do the job, with the reason written down.
Local part
An app part with no base match. Logged as a candidate to add to the base later.
Full set
A wrap includes every variant of its base part (sizes, states, styles), not only the ones screens use today.
Starter wraps
The 15 wraps already in the Tier 2 Template, such as Button, Header and ListItem. A new app renames and restyles them.

Checking

Batch
One unit of work: one flow section, one set of parts or one rule reapplied. The done check runs after each batch.
Done check script
A script stored in the base file that counts rule breaks across a whole file: unbound colors, raw spacing, missing text styles, detached parts and more.
Reapply scan
After a new rule or pattern, the agent searches the whole file for the same job and applies the rule everywhere, not only on the new screen.
Fallback color
The raw color Figma stores behind a color variable. A wrong one looks fine in screenshots, which is why counts come before the screenshot.
